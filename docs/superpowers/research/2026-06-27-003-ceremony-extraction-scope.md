## Ceremony map (per area)

### passkey

WebAuthn passkey payment authorization ceremony — same-device (Touch ID / Windows Hello) and cross-device (FIDO caBLE) registration-as-authorization, with stateless nonce/replay protection and amount-integrity gates. Located at `/payment-gate/passkey/`, mounted on Express app by `registerPasskeyGate(app)` in app.ts. Single registration ceremony (not register-then-authenticate); order is ephemeral (stateless, URL-encoded); challenge rides in a signed token; mandate is AP2-shaped but dev-signed; settlement optional (Hedera testnet, demo-mode).

**Modules**
- payment-gate/passkey/verify.ts — buildRegistrationOptions (generates options + signed challenge token) and verifyPasskeyAssertion (verifies registration response, yields VerifiedAuthenticator)
- payment-gate/passkey/routes.ts — HTTP route handlers: GET /payment-gate/passkey (renders page), GET /payment-gate/passkey/options (returns options + challenge), POST /payment-gate/passkey/verify (verify + gates + complete), GET /payment-gate/lib/sw/* (serves @simplewebauthn/browser ESM same-origin)
- payment-gate/passkey/page.ts — renderPasskeyPage() server-renders HTML with order table, toggle for cross-device, @simplewebauthn/browser integration, and receipt rendering (gates + settlement)
- payment-gate/passkey/page.test.ts — verifies page rendering with order details, toggle links, xdev param
- payment-gate/passkey/page-settlement.test.ts — verifies receipt rendering (gates, settlement detail, QR, HashScan link, demo honesty statement)
- payment-gate/passkey/routes.test.ts — tests route handlers, bad tokens, cross-device toggle, @simplewebauthn/browser serving
- payment-gate/passkey/verify.test.ts — tests buildRegistrationOptions (same-device vs cross-device attachment)
- payment-gate/passkey/verify.fixture.test.ts — fixture-based integration test for verifyPasskeyAssertion (recorded registration response)
- payment-gate/challengeToken.ts — issueChallenge (generate 32-byte challenge + HMAC-SHA256 signed token) and verifyChallenge (verify signature + expiry, recover challenge). Stateless: no server memory, serverless-correct
- payment-gate/mandate.ts — buildPasskeyMandate (create AP2-shaped mandate from order + authenticator + origin; add mock signature), buildBindingFields (extract amount/currency/payee/orderId), runGates (four validation gates: amount integrity, authorization present, user verification asserted, subject credentialID binding)
- payment-gate/origin.ts — deriveOrigin (extract rpID and origin from req.headers x-forwarded-* or host/protocol; honors Vercel TLS termination)
- payment-gate/completion.ts — completeOrder (idempotent order recording, re-pricing check via catalog, optional settlement, cart clear, verification state clear)
- checkout.ts — encodeOrder (base64url JSON), decodeOrder (decode + shape validation, unsigned/tamperable)
- catalog.ts — Order interface, createOrder (build order from cart items), getProduct (catalog lookup for re-pricing)
- verificationStore.ts — VerificationStore interface, per-orderId age/loyalty state (MemoryVerificationStore or RedisVerificationStore)

**Routes**
- GET /payment-gate/passkey?order=<token>[&xdev=1] — Render passkey gate page (with order table, amount, toggle for same/cross-device, 'Back to checkout' link). Status 200 on valid token, 404 on invalid/bad currency
- GET /payment-gate/passkey/options[?xdev=1] — Return WebAuthn registration options + signed challenge token. {options: RegistrationOptionsJSON, challengeToken: string}. No request body; xdev=1 sets authenticatorAttachment='cross-platform' to force caBLE
- POST /payment-gate/passkey/verify — Verify passkey assertion. Request: {response: RegistrationResponseJSON, challengeToken: string, orderToken: string}. Response: {mandate: PasskeyMandate, gates: GateResult[], completed: boolean, settlement?: SettlementRecord, settlementError?: string, binding: BindingFields, reason?: 'gates'|'reprice'}. Status 400 on invalid token/challenge, 403 if age verification required (before completion check)
- GET /payment-gate/lib/sw/* — Serve @simplewebauthn/browser ESM from same-origin path (no CDN). createRequire resolves package, walks to /esm, fails at startup if missing

**What mount() must expose / inject**

**mount() interface for @openmobilehub/attesto-gate feature 003:** registerPasskeyGate(app) is currently called directly in app.ts; extraction requires:

1. **app.locals.attesto** — Attesto mount must expose:
   - **store: VerificationStore** — per-order age/loyalty verification state (same interface used by credential-gate for isAgeUnverified check)
   - **walletOrigin: string** — (future: DC payment gate may need this for cross-origin validation)

2. **process.env.GATE_SECRET** — HMAC key for challenge token signatures. Dev: per-process random (fine because single process spans issue+verify). Production: **required stable value** on serverless (different instances may handle options vs verify)

3. **Origin binding inputs** — deriveOrigin(req) reads:
   - `req.headers['x-forwarded-host']` and `req.headers['x-forwarded-proto']` (Vercel TLS termination)
   - Falls back to `req.host` / `req.protocol`
   - Produces `{ rpID: string, origin: string }` for WebAuthn binding

4. **Order encoding seam** — passkey/routes.ts decodes order via `decodeOrder(orderToken)` from checkout.ts:
   - Input: unsigned base64url-JSON token (tamperable)
   - Output: Order interface (shape-validated only)
   - Coupling: must also wire in `isAgeUnverified()` check from checkout.ts before completion

5. **Completion seam** — completeOrder() (from payment-gate/completion.ts) requires:
   - Order model (lines, total, currency, id)
   - Catalog for re-pricing (createOrder, getProduct)
   - cartStore + orderStore for idempotent recording
   - verificationStore for loyalty/age re-derivation
   - Optional: Hedera settlement config (env vars read inside completeOrder)

**Extraction boundary:** The ceremony itself (verify.ts, routes.ts, page.ts, challengeToken.ts, mandate.ts) is cleanly isolated. The dependencies (order model, verification store, catalog, completion) must be injected as interfaces or app.locals seams so the gate doesn't hardcode imports to demo-specific modules.


**Trust model (real vs presence-only-demo)**

**Real/Cryptographically verified in v0.1:**
- WebAuthn registration ceremony — @simplewebauthn/server verifies attestation object, credential public key, clientData JSON signature. userVerification asserted by authenticator hardware.
- Challenge nonce — HMAC-SHA256 signed token, time-limited (120s default, configurable), timing-safe comparison. Replay impossible without valid signature + within expiry window.
- RP-ID / origin binding — generateRegistrationOptions pins rpID and origin; verifyRegistrationResponse enforces matching origin and rpID in clientData. Cross-origin attestations rejected.
- Credential device type and backup eligibility — attestation returns credentialDeviceType ('singleDevice' vs 'multiDevice') and credentialBackedUp; not trusted for authorization (only surfaced in mandate), but real metadata from authenticator.

**Presence-only / demo-only in v0.1 (fenced, not presented as safety control):**
- Mandate signature — "MOCK-DEV-SIGNER" field contains only SHA256 digest of mandate body, not cryptographically signed. Production AP2 spec requires KB-JWT (key-bound JWT); deferred to v0.2.
- Amount cryptographic binding — passkey ceremony does not cryptographically sign the amount (that is the Digital Credentials payment gate's job via OpenID4VP). Passkey amount binding is a consistency check: Gate 1 re-sums cart lines and verifies lines.sum == total == payment.amount. A tampered order token claiming a different total fails the re-pricing check in completeOrder().
- Settlement via x402 on Hedera testnet — demo peg (1 USD = 1 HBAR), tiny token amounts, no real money moves. Page renders "test network" and "demo" clearly; settlement record carries this metadata (fxRate = "1 USD = 1 HBAR (demo peg)").
- Mdoc trust verification — not implemented. Age credential gate uses fail-closed disclosure + binding (nonce) but does NOT verify issuer/device signatures per ISO 18013-5. Acknowledged as future work (v0.3+).

**Grid:**
- userVerified ← cryptographically verified (authenticator assertion)
- rpID/origin binding ← cryptographically verified (clientData signature)
- challenge nonce ← cryptographically verified (HMAC-SHA256)
- amount binding (passkey) ← re-derivation check, not cryptographic
- mandate signature ← presence-only (dev hash)
- settlement finality ← real on-chain via Hedera (but on testnet, tiny demo amounts)
- age credential claims ← disclosure + nonce binding, not issuer trust

**Extraction risks**

1. **@simplewebauthn/browser ESM path hardcoding** — routes.ts serves from `/payment-gate/lib/sw/` (same-origin requirement). Extraction must either (a) keep this path convention, (b) make it configurable via options, or (c) move it outside payment-gate. Current: createRequire resolves package, fails at startup if missing — extraction must preserve this validation.

2. **Order token tampering and re-pricing coupling** — Order is unsigned base64url JSON (hand-editable). Routes decode with shape validation only; invariant 2 requires completeOrder() to re-price via catalog. Extraction must ensure both checks run: decodeOrder is permissive, but completeOrder calls createOrder(lines) and compares total. Risk: if completeOrder is not called or is bypassed, a tampered token (fake discount) passes the gate.

3. **Per-order verification state scope** — verificationStore is keyed by orderId; Invariant 4 requires no cross-order bleed. Passkey /verify calls `isAgeUnverified(order)` which reads from store; if store is misconfigured (e.g., shared global key instead of per-order), all orders inherit one shopper's age state. Extraction must wire the store interface, not a singleton.

4. **GATE_SECRET production stability** — dev uses per-process random; production requires stable shared value across serverless instances. Challenge tokens fail verification if instances don't share the secret. Extraction must document this as a required env var + provide selection logic (current code at bottom of challengeToken.ts is correct, but adopters easily miss it).

5. **Origin derivation and x-forwarded-* headers** — deriveOrigin reads x-forwarded-host/proto on Vercel but req.host/protocol locally. Misconfig (e.g., missing x-forwarded-* on prod, or spoofed headers on plain HTTP) breaks rpID/origin binding. Extraction must document this, validate at mount time (fail if origin is plain HTTP and not localhost).

6. **Mandate signature is dev-only** — "MOCK-DEV-SIGNER" signature field is a simple SHA256 digest. Extraction must clearly mark this as not for production and signal v0.2 path (AP2 SD-JWT signing). Adopters must not ship this as a real authorization proof.

7. **Settlement is optional but side-effecting** — completeOrder runs settlement if Hedera env vars are set. Configured-but-failed settlement means authorized-but-not-completed (no order record, cart stays). This is correct, but the separation of concerns is fragile: if mount() provides a settlement handler, it must be reliable or idempotent. Extraction must document failure modes and idempotency guarantees (current: only most-recent order is replay-protected; concurrent verifies may settle twice).

8. **Age verification check inlined in /verify** — isAgeUnverified() call at line 69 of routes.ts reads from verificationStore and refuses before gates. Extraction must decide: (a) keep this call (require isAgeUnverified as an injected function), (b) move it to completeOrder (cleaner, but changes flow), or (c) let mount() wire it. Current coupling: routes.ts imports from checkout.ts; must be inverted.

9. **Catalog re-pricing in completeOrder** — getProduct() and createOrder() calls in completion.ts are tightly coupled to the demo's catalog module. Extraction must inject or abstract these: either (a) accept a `repriceOrder(order)` function, (b) accept a Catalog interface, or (c) require caller to call a validation step before completeOrder. Risk: adopter provides wrong catalog, silent under-charge.

10. **Cart and order store coupling** — completeOrder clears cartStore after writing orderStore. If these are out of sync (e.g., different backends for different orders), cart-clear for order A might wipe order B's cart. Current design: cartStore is shared (one cart per session), orderStore is per-order. Extraction must document this invariant and validate at mount.

11. **Hedera settlement sidecar dependency** — settleOrder() from hedera-settlement/ calls out to a facilitator (blocky402). Configuration is in env vars (HEDERA_OPERATOR_ID, HEDERA_MERCHANT_ACCOUNT_ID, etc.). Extraction must (a) document these as required for settlement, (b) allow mount() to inject a custom settler or disable, (c) handle facilitator timeouts/failures honestly (done: returns settlementError).

12. **Challenge token expiry hardcoded to 120s** — issueChallenge uses DEFAULT_TTL_MS = 120_000. Extraction should allow configuration but must validate that expiry is sensible (e.g., reject negative or year-long TTLs). Current code is fine, but extraction should make it a mount option.

13. **RP_NAME hardcoded to "Product Picker"** — generateRegistrationOptions uses const RP_NAME = "Product Picker". Extraction must make this configurable (e.g., merchant name, store name). Low risk, but impacts UX (appears in biometric prompt).

14. **Cross-device (caBLE) toggle is UI-driven, not enforced** — xdev=1 param on /options and /passkey page routes controls authenticatorAttachment. No server-side enforcement; a client could request cross-device options but use same-device assertion. Not a security issue (authenticator type is in attestation, not a security boundary), but extraction should document this as client-side UX preference, not a security control.

15. **Stateless design is correct but fragile to misuse** — order + challenge are URL/token-carried, no server memory. This is intentional (serverless-correct), but extraction must warn adopters: (a) don't add server-side session memory for orders (breaks scoping), (b) do use a stable, shared GATE_SECRET, (c) order tokens are stateless but settlement idempotency check relies on orderStore (last-order-only; acceptable for demo, not for high-volume).

**Concrete extraction checklist:**
- [ ] Move verify.ts / routes.ts / page.ts to @openmobilehub/attesto-gate passkey submodule
- [ ] Inject store interface via app.locals.attesto.store

- [ ] Inject age-check function or move to completeOrder

### credential-gates

credential-gates (payment-gate/credential-gate/ + payment-gate/dc-payment/) — Digital Credentials API + OpenID4VP for age-verification and loyalty-discount, with amount-bound mdoc payment authorization

**Modules**
- payment-gate/credential-gate/dcql.ts — DCQL query builders for age (age_over_21, age_over_18) and loyalty (membership_number, tier) credentials
- payment-gate/credential-gate/request.ts — Build signed OpenID4VP request (reader cert SAN + encryption key, no transaction_data)
- payment-gate/credential-gate/verify.ts — Decrypt JWE response, decode mdoc, evaluate credential claims (age >= minimumAge, membership != null), record in verificationStore
- payment-gate/credential-gate/routes.ts — HTTP routes: GET /credential-gate/:kind (render page), GET /request (issue signed request), POST /verify (evaluate + record), POST /demo (instant demo if DEMO_MODE=1)
- payment-gate/credential-gate/page.ts — Server-rendered HTML for age/loyalty gate, navigator.credentials.get({digital}) flow, fallback to instant-demo button
- payment-gate/dc-payment/mandate.ts — AP2-shaped DC payment mandate with 4 deterministic gates: (1) amount binding (hash + amount/currency/payee match), (2) authorization present (issuerAuth + deviceAuth), (3) credential not expired, (4) subject binding (instrument id matches)
- payment-gate/dc-payment/request.ts — Build signed OpenID4VP request with transaction_data (amount + currency + payee bound), reader cert, ephemeral ECDH key for response encryption
- payment-gate/dc-payment/verify.ts — Decrypt JWE response, extract wallet-signed transaction_data_hash, build DC mandate, run 4 gates, check isAgeUnverified server-side, write to orderStore on success
- payment-gate/dc-payment/routes.ts — HTTP routes: GET /payment-gate/dc-payment (render page), GET /request (issue signed request with txData), POST /verify (gates + order completion)
- payment-gate/dc-payment/page.ts — Server-rendered HTML showing order total, cross-device QR code via navigator.credentials.get({digital}), fallback to passkey gate, marks amount as 'amount-bound' in copy
- payment-gate/dc-payment/mdoc.ts — Structural-only CBOR decode of mdoc DeviceResponse (no issuer/device signature verification, future work); extracts disclosed claims and transaction_data_hash from deviceSigned namespace
- payment-gate/dc-payment/txData.ts — Transaction data envelope (type urn:eudi:sca:payment:1) with amount, currency, payee id (rpID), transaction_id; encodes as base64url; buildTransactionData() derives amount + payee from order + origin
- payment-gate/dc-payment/readerContext.ts — Seals ephemeral ECDH private key + transactionDataB64 + nonce in JWE (dir/A256GCM, 3min TTL) under GATE_SECRET; /verify decrypts to recover keys for wallet response decryption
- payment-gate/mandate.ts — buildBindingFields() tying payment amount to origin.rpID + payee name; buildPasskeyMandate() constructs passkey mandate with 4 gates (amount integrity, auth present, user verification, subject binding)
- payment-gate/origin.ts — Derive rpID (host without port) and origin (<proto>://<host>) from request headers (x-forwarded-proto, x-forwarded-host), used for reader cert SAN and payee binding
- payment-gate/challengeToken.ts — HMAC-signed (GATE_SECRET) ephemeral challenge tokens for WebAuthn flow; issued by /passkey/request, verified on /passkey/verify
- checkout.ts — isAgeUnverified(order) server-side gate (enforced on /checkout/place-order and POST /verify endpoints); encodeOrder/decodeOrder (unsigned base64url token codec); checkoutResponse() renders page with verification state + loyalty discount applied; ageApproveUrlForOrder()
- catalog.ts — requiredAgeForLines() extracts max minimumAge from order lines; LOYALTY_DISCOUNT_PCT = 10; Product.minimumAge metadata for alcohol (21+) and age-restricted categories
- verificationStore.ts — VerificationStore interface + MemoryVerificationStore (Map per orderId) and RedisVerificationStore (key product-picker:verification:{orderId}); per-order scope prevents cross-user bleed; read/write/clear methods

**Routes**
- GET /credential-gate/:kind — Render age/loyalty gate page (kind=age|loyalty); feature-detects navigator.credentials; renders instant-demo button if DEMO_MODE=1
- GET /credential-gate/:kind/request — Issue signed OpenID4VP request for credential (age: age_over_21 + age_over_18; loyalty: membership_number + tier); returns {request, readerContextToken} with sealed nonce
- POST /credential-gate/:kind/verify — Decrypt JWE response, decode vp_token, evaluate claims (age >= minimumAge OR age_over_21===true; loyalty: membership_number != null); check nonce binding (apu/apv); record in verificationStore if verified; return gates array
- POST /credential-gate/:kind/demo — Instant demo (DEMO_MODE=1 only); record verified state without credential exchange; fenced endpoint for demo deployments
- GET /payment-gate/dc-payment — Render amount-bound payment gate page; shows order total and 'authorize on phone' copy; feature-detects Digital Credentials API; offers fallback to passkey gate
- GET /payment-gate/dc-payment/request — Build signed OpenID4VP request with transaction_data (amount + currency + rpID payee); request signed with reader cert SAN=rpID; returns {request (JWT), readerContextToken (sealed ECDH key + txDataB64)}
- POST /payment-gate/dc-payment/verify — Decrypt JWE response with sealed ephemeral key; extract transaction_data_hash from wallet's deviceSigned mdoc; run 4 gates (hash match, auth present, not expired, subject binding); check isAgeUnverified server-side; write orderStore + clear cart + clear verificationStore on all-gates-pass

- GET /checkout/order-status — Poll endpoint for embedded widget; returns completed order if orderStore has matching orderId; read-only

**What mount() must expose / inject**

**From app.locals/mounts needed:** GATE_SECRET (env var or secret store); verificationStore instance (MemoryVerificationStore or Redis); cartStore instance; orderStore instance; origin/rpID derivation (x-forwarded-proto, x-forwarded-host headers). **Needs from host app:** order.id scoping for per-order verification state (already in order token); WebAuthn/Digital Credentials API rpID matching (reader cert SAN must equal derived host rpID, or verifications fail); DEMO_MODE env var gating for instant-demo endpoints; ageVerified + loyaltyApplied flags passed to checkoutResponse (derived from verificationStore.read). **Coupling to demo:** verificationStore namespace is hardcoded as "product-picker:verification:{orderId}" in RedisVerificationStore — namespace collision risk on shared Redis; catalog Product.minimumAge for age-restricted products (alcohol 21+); LOYALTY_DISCOUNT_PCT constant (10%) synchronized across checkout recomputeOrder(), mandate.ts Gate 1, and passkey Gate 1 logic

**Trust model (real vs presence-only-demo)**

**REAL (cryptographically verified):** OpenID4VP request signing (reader cert with X.509 SAN=rpID, signed with ES256 ECDSA P-256); wallet's response encryption (to server's ephemeral ECDH public key, confuses captured responses); amount binding for DC payment (wallet signs SHA-256(transaction_data_base64url) where transaction_data includes order.total, currency, origin.rpID payee; Gate 1 re-derives hash from sealed txDataB64 and matches wallet's signed hash); nonce binding for credential gate (response apu/apv values checked against request nonce, or empty/absent is accepted; no token-presence fallback); explicit positive claims (age: age_over_21===true OR age_in_years >= minimumAge, NOT token-presence fallback; loyalty: membership_number != null && trim() !== ''); server-side enforcement on EVERY completion path (isAgeUnverified enforced on /checkout/place-order AND /payment-gate/dc-payment/verify AND /credential-gate/age/verify). **DEMO/PRESENCE-ONLY (not cryptographically verified):** Mdoc issuer/device signature verification — mdoc.ts explicitly says "NO trust verification: does not check issuer/device signatures"; wallet signatures on transaction_data not verified (future work per CLAUDE.md comment); passkey mandate marked "0.1-mock" with MOCK-DEV-SIGNER (not real AP2 SD-JWT); instant-demo endpoints (/credential-gate/:kind/demo, /payment-gate/passkey instant-demo, /checkout/place-order instant-demo) are fenced behind DEMO_MODE env var and marked in gate records with detail='instant demo' / 'skipped' to indicate no device authorization occurred

**Extraction risks**

**verificationStore scoping:** MemoryVerificationStore uses Map&lt;orderId, Verification&gt;; RedisVerificationStore keys are hardcoded as 'product-picker:verification:{orderId}'. If extracted to shared app context (app.locals), must ensure Redis namespace is unique or will collide with other demos. **Order token is unsigned:** order token is base64url JSON, hand-editable; ALL payment amounts must re-derive from order.total at verification time, not trust token. Gate 1 (passkey/dc-payment) re-sums lines and re-checks discount is exactly LOYALTY_DISCOUNT_PCT; this is load-bearing. If discount applied in checkout but not recognized by payment gate, amount mismatch blocks completion. **GATE_SECRET**: used by both WebAuthn challenge tokens (passkey) and reader context encryption (dc-payment, credential-gate); must be externally managed in production (Vercel env vars); if extracted, needs wired into app's secret store or shared GATE_SECRET. **Origin/rpID binding:** reader cert SAN must match derived rpID from headers, or WebAuthn verification fails; if extracted app uses different hostname derivation logic, rpID mismatch breaks reader cert verification. **Loyalty discount reconciliation:** LOYALTY_DISCOUNT_PCT (10%) hard-coded across three locations: checkout.ts recomputeOrder(), mandate.ts Gate 1 check, passkey/dc-payment Gate 1 logic; if discount changes, all three must be updated or gates will reject legitimately-discounted orders. **Feature detection:** both renderDcPage and renderCredentialPage feature-detect navigator.credentials && window.DigitalCredential (Chrome 141+ for DC API); without it, pages fall back to passkey or instant-demo; if extracted, must preserve fallback chain or gate becomes unavailable. **Instant-demo security:** demo endpoints are fenced behind DEMO_MODE env var (checked per-request in routes.ts); production deployments MUST NOT set DEMO_MODE=1 or the /credential-gate/:kind/demo and passkey instant endpoints become anonymous toggles of safety flags, bypassing all cryptography. **Discount order-scoping:** checkout recomputeOrder(loyaltyApplied) rebuilds order with new total; payment gates bind to this recomputed total. If checkout and payment gates use different loyalty state, they will disagree on binding amount (one includes discount, other doesn't) and one will fail Gate 1.
